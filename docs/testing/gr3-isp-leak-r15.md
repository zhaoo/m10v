# r15：漏光端点方向修正候选

仅 GR III 2.10 / GR IIIx 1.60，未合并、推送或部署。
用户否决 r14 漏光：整张照片发白，缺少早期版本的单侧漏光。
本轮不把主机拟合图当成 ISP 实拍，不重新调整强度、范围或历史纹理来掩盖症状。

## 已证实的缺口

r14 主机模型假设 `A(src)*(1-weight)+B(src)*weight`，把原图 identity
放在 A/C，把提亮/暖色端点放在 E/F。实际原厂表和接线可证明 A/C、E/F 两组
分别装入高于/低于 identity 的曲线，B/D 使用单调0..255的随机权重曲线；
**但这些控制数据本身不能独立证明权重0时芯片到底选择哪组。**

另一个可证实的模型错误：r14 预览只更新选中的 Cb 或 Cr，而相机端每次处理的
是交错 UV 的两个字节，每个字节都经过同一组曲线。未选字节的权重为0；
如果0权重不对应 identity，另一字节也会被修改。此前主机预览遗漏了这一传播。

## 最小候选修改

本轮只交换9组漏光的效果/identity端点，以及1组亮度调制的零/原遮罩端点。
采用 `upper*weight+lower*(1-weight)` 方向，令空间权重0对应 identity，
令亮度调制为 `mask*(1-original_Y)`。这个方向与整张泛白的反馈一致，
现有证据支持实机检验，**尚未测得芯片端点输出，不能把它写成已确定根因或已实机修复**。

没有修改 native C、钩子地址、原厂图连接、等待/完成/释放、缓存契约、工作区、
存档ABI、菜单、颗粒或模糊。早期漏光的平方边缘衰减、随机起伏、左右/竖拍资源和
强度/范围映射完全保留。本次效果无 CPU 像素读取、处理或 RNG，仍使用相同 ISP 步骤。

## 验证

- 修改前的端点检查出现2个预期失败，记录在 red-endpoint-tests.log。
- 主机模型现完整模拟两种 UV 字节经过两次色度处理；覆盖所有256种输入值、
  未选通道、左右单侧、三种范围/强度、纯白及0权重区域。
  在该方向假设下，r14原端点可复现0纹理区域的大幅提亮，r15在此区域保持原值。
  这是候选一致性检查，不是独立的硬件算术证明。
- 167项相关host/ARM回归通过；Node纯ISP检查7项通过。
- 最终BIN检查另验证实际交付曲线的端点、真实原厂任务/完成/JPEG交接和零CPU像素访问。
  硬件与内核端点是明确的服务替身，不模拟芯片像素计算，也不证明实际回放速度。
- 最终构建与r14比较钩子、纹理、工作区及代码布局，核验除了曲线和构建身份外没有其他变化。
  详细结果与源码指纹保存在 final-validation.log。
- 两机型最终BIN各13项检查通过。GR III build_id=`43384071`；IIIx=`9411d4c3`。
- 全仓npm未重跑；最近r14基线为484项、411通过、48失败、25跳过，不能称全仓通过。

## 实机检验

保留同机型r14/r13恢复包，按README安装。先关闭颗粒、模糊及HDF，固定曝光和白平衡：

1. 漏光关闭拍一张作为对照。
2. 漏光中档、范围窄、左侧拍一张；再切右侧拍一张。
3. 重点检查与漏光相反的一侧是否保持原片明暗/颜色，暖色是否随左右选择移动，
   而不是整张一起发白；再试中/宽范围和竖拍。
4. 检查即时回放、相册及连续三张。性能和画质均待此次实拍，不沿用r13的速度验收。
