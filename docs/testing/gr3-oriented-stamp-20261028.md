# GR III / IIIx per-exposure oriented stamps

Scope: approved Task 2, GR III 2.10 and GR IIIx 1.60. This is offline evidence; camera timing, actual JPEG appearance and hardware performance still require user validation. No image plane, image dimensions, EXIF or RAW data are rotated or replaced.

## Data and ownership

The original per-frame `ShootingInfo+0xc8` supplies direction. The original field setter/getter at `0x53491530/0x53491528` operate on this byte. Before-exposure metadata producer `0x534322d8` receives this shooting record in r2 and writes its date/time at `+0x944..0x94b`. The EXIF setter `0x535f63d0..d4` binds the same record's `+0xc8`; `0x535f67ac..dc` reads it and maps values 1/2/3 through `0x53d30190` to EXIF 8/3/6. Invalid values map to landscape. The builder checks the exact official RTOS hash, eight instruction preimages, and that table.

The already-installed original processing-task ingress at `0x5351ea9c` freezes this recipe's shooting byte at its first enqueue, alongside its existing selection snapshot. It never reads a later live/UI direction or uses a shared last-shot stash. Subsequent producer calls preserve the first snapshot. The stamp getter validates recipe, trace, snapshot version/size/status, owner, shooting identity and normalized direction before returning it; missing or invalid ownership returns landscape.

The sole extended recipe allocator owns these disjoint ranges:

| Owner | Offset | Bytes |
| --- | --- | --- |
| Original recipe | 0 | 0x4778 |
| Existing save trace | 0x4778 | 656 |
| Existing color owner | 0x4a08 | 1796 |
| Existing RAW token, including existing HDF reserved words | 0x5110 | 48 |
| New stamp record | 0x5140 | 16 |

The allocation is now `0x5150`; no existing offset moves. Compile-time size/extent assertions and builder storage checks prevent overlap. The allocator initializes the complete appended extent and retains the original allocator failure behavior. The current pipeline test allocates the extent declared in the manifest, so a future owner extension cannot silently overwrite the next Make object.

`m10v_library_image` and persistent 184-byte film state retain their existing ABI. An explicit transient render context carries direction, completion and optional custom LUT/name. Existing render APIs keep landscape behavior. Four-corner layout, date/date-time, right-aligned second line, colors, glyphs, scaling and small-image skip rules remain. Logical glyph coordinates map individually into the original Y/C planes. Chroma sampling happens after the transform, and an incomplete final pair at an odd visible width is skipped. The public renderer retains its existing rejection of odd width/stride before mutation.

The disabled capture fast path returns before creating the stamp render context, pixel reads/writes, cache operations or allocation.

## Verification

- Before implementation, focused existing host stamp tests failed because their ctypes film state is still the historical five-slot/104-byte ABI. `test_short_film_name_aligns_with_date_at_right_corners` raised an empty-array `IndexError`; `test_stamp_fits_corners_small_aspects_long_ascii_and_two_lines` found zero glyph pixels. Those old fixtures/assertions remain unchanged.
- New tests were observed red when the oriented stamp entry was absent, then green with the implementation. Correct current 184-byte state fixtures are used. Three landscape golden hashes were independently generated by compiling unmodified baseline C with that current state ABI; date/name layout remains byte-for-byte equal.
- `.venv/bin/python -m unittest tests.test_gr3_stamp_orientation tests.test_gr3_capture_raw_lifetime tests.test_gr3_capture_lifetime`: **19 passed**. The new orientation suite includes host four-direction/four-corner/date/date-time/two-line tests, odd/tiny/padding/unknown/invalid-date tests, public odd-layout rejection, original EXIF mapping, original exposure clock writes, genuine original task enqueue followed by delayed UI rotation and actual Still Make/capture glyph rendering, aliased main/secondary descriptors, sole allocation ownership and unmapped 24MP disabled capture. The convenience fixture snapshot is erased before the genuine enqueue; neither native completion nor final direction is synthesized.
- `.venv/bin/python scripts/check_gr3_oriented_stamp_sanitizers.py`: **140 layouts passed ASan/UBSan and row/tail guards**, including 24MP and tiny odd widths/strides.
- Debug/profile runtime compilation for both `camera_model='gr3'` and `'gr3x'` passed, including `m10v_library_render_oriented_profiled` and the 0x5150 extent. These are runtime link checks, not final official firmware package readbacks.
- `tests.test_gr3_capture_lifecycle_integration` retains a preexisting stale allocator expectation `0x50f0` (the prechange runtime was already `0x5140`), so its allocation assertion fails against the current `0x5150` contract. It is not reported as passing or weakened. The new explicit allocator test covers the current extent and unchanged stock prefix.

Final whole-package identity, paired III/IIIx export/readback and complete integration tests are controller-owned delivery gates. Camera acceptance remains pending.
