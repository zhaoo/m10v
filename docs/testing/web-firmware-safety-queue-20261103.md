# 网页严格校验与排队候选（2026-11-03）

## 实现状态

以 GitHub main `711ce5163ef2eb5ba690c1abdfadbd8a94529c43` 为基线，在 `daily/firmware-safety-audit` 本地实现。用户明确选择完整重建校验，并选择一并接入任务队列、进度和取消。没有合并、推送、生产部署、写卡或操作相机。

原生代码、生成器和两个支持机型的目标布局未改。网页只支持精确官方 GR III 2.10 / IIIx 1.60；周年固件、第三方/未知机身来源和抬版本继续拒绝。GR IIIx 的旧网页版本适配控件也保持关闭；离线版本研究函数仍保留。

## 真实生成与下载链路

1. 配置预检固定官方源 SHA、机型、版本和配置/源码指纹。机身信息仍是用户声明，无法读取机内 Flash 或验证第三方持久化设置。
2. 提交生成任务时，服务端再次核对机身型号/公开版本/来源。自报已装 M10V 时要求此前实测包 SHA 记录。项目 URL 的受支持 SHA 不能掩盖存储中另一个机型的官方字节。
3. 同一队列任务内执行第一次完整生成，再按相同来源和配置第二次完整生成。开关机图片等覆盖也包括在最终重建中；最终 BIN 必须逐字节相同，严格解码、组件版本和回执绑定全部通过。
4. 统一下载出口只接受服务端本次验证器签发的内存记录，并在发送前重新核对实际字节 SHA/长度。独立执行线程的结果须在 HTTP 主线程再次绑定来源、配置和完整文件，不能用客户端 JSON 伪造通过记录。
5. 浏览器收到真实 Blob 后计算 SHA-256，核对来源、配置、机型、文件名、长度和服务端记录。任何缺失或不一致都不创建下载 URL。完成页“再次下载”也重新验证；修改配置、切换来源、取消和离开页面会停止旧任务/旧下载。
6. 官方备份先严格核对精确原包及 ZIP 内原件，再在浏览器验证归档摘要。旧 edit / 800T / 关机图导出同样进入队列、第二次重建和统一下载出口，没有遗留直出 BIN 的旁路。

服务端报告分别使用 `download_allowed=true` 与 `installation_allowed=false`、`camera_tested=false`。允许下载只证明文件核查通过，不是相机刷入安全认证。

## 队列和响应性

- 默认一个任务运行，覆盖生成和严格重建两个阶段；最多 4 项排队。超出容量拒绝，不无限占用内存。
- 页面显示排队位置、生成、重建验证、接收/摘要校验。排队任务取消后不执行；运行任务取消后等执行线程清理完成，才开始下一项。
- 使用 24 字节随机任务 ID，状态接口不返回 BIN/回执。结果默认保留最多两份、合计 96 MiB，单份上限 70 MiB；3 分钟过期，访问队列时清理；元数据最多 32 项。
- 异步提交/轮询/下载避免长时间占住单个 HTTP 构建请求。同步旧接口仍使用同一个队列。
- 完整生成与校验在专用 Worker 线程执行，HTTP 主线程负责接单、状态与取消。真实回归曾在同线程实现下两次复现状态轮询 `ECONNRESET`；移出同步构建/审计计算后，双机型完整链路通过。没有通过忽略校验、重试生成或降低断言掩盖问题。
- 默认构建并发仍为 1；没有生产 Linux 内存/峰值负载测量，不将本机结果当作提升并发数的依据。前端本地编译需迁移 Python/LLVM/验证链，未在本轮替换。
