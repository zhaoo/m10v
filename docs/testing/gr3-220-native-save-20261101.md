# GR III 2.20 原生胶卷保存修复与发布核验（2026-11-01）

## 结果及授权

用户报告官方 2.20 能导入但无法保存，随后明确要求“没问题就合并main发布github和宝塔”。本次按该指令在软件核验完成后发布；没有相机、SD 卡刷入或用户实机验收证据，不把下载成功或 ARM 模拟执行称为实机验证。

起点为生产提交 `ef92d9f39010b4a9cbc681549854275c54e6bdf4`。本次使用 App 的独立工作树；原包及构建产物均不提交 Git。

## 根因与边界

1. 前次修复保留上传固件，但完整原生胶卷仍只适配 2.10。2.20 中代码、初始化数据和资源目录存在不同偏移，不能靠取消门禁、统一加偏移或改版本号完成适配。
2. 保存链路在没有启用开关机图片时仍调用旧 ABI 门禁，直接构建通过也会在实际保存接口被拒绝。空图片操作现在只验证容器及输入身份；选择自定义图片仍要求已经适配的原生布局。

新增精确绑定真实官方 2.20 的目标描述。编译阶段收集有类型的分支、指针及 MOVW/MOVT 引用，区分代码、数据与图片资源；以现有 2.10 编译及独立审计结果为输入，把引用和原厂补丁位置重定位至实际上传的 2.20。不复制参考包的原厂分区。

目标核验覆盖启动复制、对象 getter 与成员关系、完整运行体 MMU 可执行映射、引用清单完整性绑定、原厂 ADJ 表、全部非补丁 RTOS 间隙及其他分区。最终 BIN 重新解包检查版本、运行体及来源。独立 Capstone 核验不依赖构建器的 ARM 解码逻辑。

默认胶卷保存可用。额外离线核验了非调试 HDF + 通用光晕 + A/B，以及单独调试包。2.20 的扩展边框、比例、水平仪、纯 ISP 胶片效果菜单、负颗粒、RAW 降噪、版本解锁、自定义开关机图片继续拒绝。调试 + HDF 会触发现有参考构建的编译问题，目标预检明确拒绝该组合。IIIx 1.70 保持未适配；未提供的真实 IIIx 1.70 测试输入仍跳过。不把这些范围描述为已经支持。

- 实际 Chrome 网页导入官方 2.20，经方案核验、免责声明确认、保存后下载成功；下载 BIN 的 SHA 与默认候选一致。此步骤曾复现第二处保存门禁问题，修复后重新成功。
- 最终只读复核未发现剩余 P1/P2 问题。
- 全量 Node：518 项，439 通过、51 失败、28 跳过。对干净基线归档在同一环境运行失败涉及的 30 个测试文件，51 个失败名称集合完全一致；没有新增失败。此处明确不宣称全量回归通过。
- 发布控制使用与 GitHub Actions 相同的 Node 与 Python 检查；最终终态及线上下载结果以本次 Actions、生产接口实际响应为准。
- macOS 资源观测不能代替生产 Linux 内存约束验证；发布仍保留三机型构建及现有资源限制，不放宽部署保护。
