## 1. 修正早期 CPU 版本假设

Renesas RX 的真实版本回复不是简单读取 CPU 头的四个字节。`0xfffe512b` 只从头 `+0x93` 读取第四段，第三段由 `CPU+0x5132` 的 `OR #0x1400,r1` 指令常量提供。

因此，早期内存模型把 CPU 头第三段20改为21、但其余 CPU 指令不动时，会出现声明 `2.20.21.28 / 1.70.21.18`，而已定位运行 getter 仍为 `2.20.20.28 / 1.70.20.18`。原局部版本探针使用了明确声明的 getter 替身，没有执行 RX，不能拿那些测试证明真实运行号也提高了。这本身不证明会黑屏，却排除了将该模型直接当作完整硬件候选。

20字节变化区还存在版本命令读取其前4字节并返回的确切路径；不能仅因长度20就称其为 SHA-1，也不能假定改 CPU 头不涉及任何其他验证。[完整 CPU 指令与 loader 记录](gr3-cpu-anniversary-delta-2026-11-03.md) 保留原字节、工具 SHA 与地址。

## 2. 新模型保留整个官方 CPU 和原组合类型

当前受限实验只在内存中修改 DSP 外层字段 `+0x38`、RTOS `+0x2038`、原版更新器的一条版本失败分支及必须的加和补数。CPU 外层字段 `+0x50` 和 CPU 的131072字节均保持新版官方原样。外层 `kind2` 保持不变；不叠加 M10V 胶卷、菜单或其他运行体。

| 内存模型 | DSP 包字段 | CPU 包字段 | 保留 CPU 的 SHA-256 |
| --- | --- | --- | --- |
| GR III | `2.20.21.28` | `2.20.20.28` | `f626854675ced81ee25b63ea1d211f5b60e291ba1231ab9e7ca866ca1a56cd38` |
| IIIx | `1.70.21.18` | `1.70.20.18` | `be0d0a8df92b3e8481fc04643496768e5560b6fe12e6487a69f1b657c9b0f527` |

上表是合成包声明，不是官方发布版本、机身实测读数或可下载固件。已知 DSP 运行号亦存在代码常量路径，不能把 DSP 包字段提高等同于实际运行号提高。

每款严格限定9个 decoded 字节变化，14个分区中13个完整保持不变。独立 Node 帧解码得到的完整 decoded SHA 与目标一致，外层、decoded 和官方 CPU 的加和及原 ARM 检查得到预期结果。

保留2429个原帧，3个帧按原包已经使用的24576字节直拷格式替换。末帧保留原 compressed 标志、长度、flags 和回指，只修改其末尾四个直接 literal checksum 字节；不再引入早期重放产生的21508字节直拷帧。当前内存流共2433帧，733个直拷帧全部长24576；这只减少一种新帧形状，不证明硬件已解压成功。

每款执行24个原 ARM 第一阶段局部版本场景，覆盖 CPU 版本单独升高时组合路径仍拒绝；再以精确旧官方包执行原厂拒绝与桥接分支准入两个场景。没有替代被测原比较指令；当前版本 getter 输入仍是显式提供的研究条件，不是相机读取结果。

**生产严格导入器仍拒绝此混合 DSP/CPU 版本内存容器，原因是 `version: component copies differ`。** 本轮没有放宽这个规则，没有把局部 ARM 允许更新升级为网页允许下载。

脚本：`scripts/probe_gr3_anniversary_preserved_cpu.py`；最终记录：`gr3-preserved-cpu-v2.json` / `gr3x-preserved-cpu-v2.json`。

## 3. 不能随意改成 DSP-only

原厂格式化矩阵按外层类型区分路径。kind2 进入 J/A/G/H；DSP-only kind0 还进入 F/I，kind1 则进入全部八个驱动；还存在 kind2 跳过的额外原始分区清空路径。已定位 DomainData 的 `F:\KB%ld.DOM` 路径，所以“省去 CPU 写入”不能直接视为更安全。

CPU 完全保留也不代表组合更新会自动跳过 CPU Flash。后续新增原 ARM 准备块执行确认：CPU启用标志来自CPU内容校验，未比较当前版本；新版官方CPU本身校验后仍令其为1。原组合路径先 CPU 后 DSP；六个CPU失败返回注入场景均停止于DSP之前，中途失败的实际恢复能力仍未知。当前研究保留 kind2，避免为减少表面改动引入额外格式化行为。[存储路径报告](gr3-downgrade-storage-2026-11-03.md) 明确区分静态可达条件与实际发生的格式化；[后续派发探针](gr3-anniversary-dispatch-2026-11-03.md) 区分原指令执行、故障注入和真实硬件。

## 4. 设置结构与 CPU loader 的新证据

四个官方包的 PARTPARA 逐字节一致；用于 UserData 等同性检查的4172字节表也完全一致，SHA `d17ff94346b67560bd7f10bedcfb3626f5d19438283a72b3c4c678c649a534a8`。真实 ARM 比较循环中，四个对侧官方表互换场景通过，首/中/末字改动的12个负例均拒绝；未执行错误默认路径或持久化写回。这收窄了布局兼容疑点，不能代替现存设置、所有 domain、字段语义或特殊服务版本的验证。

进一步限定追踪的 RX `0x7f` 收包/写入链及复制到 RAM 的 loader 在四个 CPU 中逐字相同；在这些已覆盖路径中没有找到“候选版本低于当前版本则拒绝”的额外比较分支。它们处理块传输字节和、握手和 FCU 状态。没有执行 RX、真实协议或 FCU，不能把“未见额外版本比较”推导为实际 CPU 已接受第二阶段，更不能扩大成不存在任何防回退机制。

## 5. 解压证据推进到哪里

三段原硬件启动/寄存器配置代码在两款新旧官方 RTOS 中是唯一的完整字节匹配。执行原 ARM 驱动前缀，实际编程虚拟 MMIO 后在原等待函数 `0x53857fd8` 前停止；原包与内存模型的模式、输入起点、输出起点一致，只因 encoded 长度不同而改变输入终点。禁用引擎的负例没有任何 MMIO 写。

没有伪造中断、硬件结果、完成长度或 Flash 成功返回；该步骤没有取得真实解压输出。先前将 `0x5362c218` 泛称“完整解析入口”也已纠正：它执行外层准入后进入解压与 decoded 加和，不等于完整分区写入状态机。

脚本：`scripts/probe_gr3_anniversary_decompress_contract.py`；记录 `gr3-decompress-v1.json` / `gr3x-decompress-v1.json`。这些记录的内存包沿用早期全字段提高模型，只用于寄存器配置前缀证据；当前 CPU 保留模型的对应 trace 在上述 `*-preserved-cpu-v2.json` 中。
