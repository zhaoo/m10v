# 2.20→2.10 / 1.70→1.60：原厂更新派发与 CPU 准备阶段

本次仅推进 GR III 官方2.20降到官方2.10、GR IIIx官方1.70降到官方1.60。新增脚本 `scripts/probe_gr3_anniversary_dispatch.py`，只读四份精确官方输入，在电脑的仿真 RAM 内运行限定原厂 ARM 代码，只输出 JSON。没有生成 BIN/ZIP、没有连接相机/SD，没有发布或开放降级下载。

## 本次变化与保护范围

| 范围 | 本次行为 | 证据等级 |
| --- | --- | --- |
| 两款降级路线 | 增加原厂路由、CPU 失败分支、旧官方 CPU 准备和分区 RAM 构造探针 | 局部原指令执行，输入为明确声明的合成对象/解码 RAM |
| 现有 GR III 2.10 | 不修改官方文件、相机运行体、生成器和默认配置；默认方案重新构建 | 产物32,267,940字节，SHA与此前验证产物完全一致 |
| 网页/严格导入器 | 本次不修改，CPU/DSP 混合版本的实验容器仍被拒绝 | 本次未重新执行网页全套回归 |
| 两阶段实际更新 | 未执行 CPU 协议、Flash 擦写、回读、断电恢复或冷启动 | 尚无设备验收；下载保持关闭 |

2.10重建的 SHA-256 为 `2d8b93b1e9e4eb1df3941fc517f6961ec23df23e3e08fb06690c2c27ac34d8ce`。原包、8个关键文件、运行体/集成源码和默认配置指纹均与保护快照匹配；临时构建完成后由既有生成器清理，没有保存新的固件文件。记录为 `builds/anniversary-downgrade-followup-20261103/gr3-210-rebuild-v1.json`。这证明所测默认产物未变，不代表新增任何相机安全保证。

## 1. 真正执行派发分支，始终停在写入体前

原入口 `0x53628db0` 与组合 wrapper `0x5362aa8c / 0x5362aac4` 在两款新版 RTOS 中完整字节一致。执行原指令，显式跳过 UI/延时，存储写入函数到达入口即停止；不会把存储调用替换成成功。主对象/组合对象、CPU/DSP 指针和启用标志均为合成 RAM 输入。

| 外层 footer kind | 原路由到达的边界 |
| --- | --- |
| 0 / 1 | DSP 写入入口 `0x5362a5b0` |
| 2 / 3 / 4 | 首先 CPU 写入入口 `0x5362971c` |
| 5 | 返回0，不进入两类写入体 |
| 6 | CPU 写入入口 |

对每款的 kind2/3/4 分别在 CPU 写入入口注入**失败返回0**，原组合路径均返回0，未进入 DSP。这里模拟的是故障返回，并未执行真实 CPU 写入失败，更不能推导物理断电后的状态或恢复能力。

当显式设置组合对象 CPU 标志 `+0x34=0` 时，原 wrapper 跳过 CPU；DSP 标志 `+0x28=1` 时继续到 DSP 写入入口。两个标志都为0时，原函数可以返回1且不进入任何写入体，所以只看该返回值也不能证明刷写成功。

## 2. CPU 标志并非“版本一样就不刷”

进一步执行 `0x5362aa14..0x5362aa54` 的原准备块，前置解码结果作为输入 RAM 提供；**不模拟前面的解压完成，也不执行完整 prepare**。执行链为：

`0x5362bd64` 查找 section kind7 → `0x5362911c` 设置 CPU 对象 → `0x53629338` 跳到 `0x536291b8` 校验 → `0x5362aa50` 把返回值写入组合对象 `+0x34`。

四个精确官方 CPU 在各自新版更新器的这个局部准备块中均令该标志为1。块内没有调用 DSP/CPU 当前版本 getter；传入的当前版本并非此块的输入。它检查 CPU 项目标识、标志及加和，不是比较当前版本后决定是否省去写入。因此，桥接模型即使保留新版 CPU 的全部字节，也不能宣称会自动跳过 CPU Flash。

| 新版更新器 | 供给的精确官方 decoded 中 CPU | CPU准备标志 |
| --- | --- | --- |
| GR III 2.20 | 2.20，CPU SHA `f626854675ced81ee25b63ea1d211f5b60e291ba1231ab9e7ca866ca1a56cd38` | 1 |
| GR III 2.20 | 2.10，CPU SHA `86745d31ec43427b56054a37bd9d47a5b60791829886da39833224cd4aa67290` | 1 |
| GR IIIx 1.70 | 1.70，CPU SHA `be0d0a8df92b3e8481fc04643496768e5560b6fe12e6487a69f1b657c9b0f527` | 1 |
| GR IIIx 1.70 | 1.60，CPU SHA `e24d2fe6962267e030fe8b05e9bb79bfcfd5c1b396bb77e6168b5d089b772b06` | 1 |

两个负例分别翻转 CPU 内容的一位、传入错误项目号，均得到标志0。它们只验证拒绝条件，不生成这种损坏包，也不把损坏 CPU 导致跳过写入当作可用方案。

这项结果补充了“新版更新器可局部接受对应旧官方 CPU”证据，不等于 RX 已收到旧版、硬件可回退或第二阶段已启动。版本准入仍需此前的桥接分支证据；原厂未修改的完整门禁仍会拒绝旧包。

## 3. 原厂 PARTPARA 构造器的 RAM 结果

执行原入口 `0x53629a94` 和真实的容量向上取整函数 `0x537fb2f8`；合成设备 vtable 明确选择原厂 `0x537fb0e4` getter，其原指令返回512。未读取真实机身几何，未调用分区表持久化写入。

两款新版各32项的容量、加载地址、跳转地址、起始扇区及两个辅助字段都与独立计算一致。额外覆盖0项、请求33项由原函数截到32项、非512整除容量向上取整，以及 bank1。bank1 测试定位出容量字段在 `+0` 共享，其余所测字段由 bank偏移 `0x434` 选取，不能把两个 bank 当成完全独立的整份记录。

所有执行中 ARM 写内存被限制在仿真 RAM；发生非 RAM 写入立即拒绝。没有把原始分区表参数与实际机身分区读回混淆。

## 复现与验收范围

```sh
.venv/bin/python -m scripts.probe_gr3_anniversary_dispatch \
  --new /path/to/official-2.20.bin --old /path/to/official-2.10.bin --model gr3 \
  --report /path/to/new-dispatch-report.json
```

IIIx 用精确1.70/1.60和 `--model gr3x`。输出仅接受新 JSON 文件，已有文件和 BIN 输出路径在读取输入前拒绝。输入 SHA 固定于对应机型；局部代码块另有 SHA preimage 校验。原厂输入身份和完整路线背景见 [汇总报告](gr3-anniversary-downgrade-followup-2026-11-03.md)。

两款 CLI 均已执行并按设计退出2，记录为忽略目录下 `gr3-dispatch-v1.json` / `gr3x-dispatch-v1.json`，均 `installation_allowed=false`、`camera_verified=false`、`stable=false`、`bin_emitted=false`。新增10项行为回归通过，包括禁止混用另一机型的旧官方包；此数字不包含前序22项，也不代表本轮重跑了全部项目测试。

目前仍缺：实际硬件解压、CPU 更新协议及 FCU 执行、DSP/CPU 擦写后回读、两阶段冷启动、现存设置和硬件恢复验收。这些依赖可恢复的专用设备；当前正常使用的2.10相机不参与试验。用户后续明确调整为完整离线验收后与网页一起发布、发布后实测；目前尚缺可交付包与独立网页链的离线验收，仍未开放下载，不能把已有研究测试通过称为设备安全证明。最新授权与缺口见 [联合发布核查](../testing/combined-release-readiness-20261103.md)。
