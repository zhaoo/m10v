# 周年原厂容器与解析器：离线证据边界

> 后续命名纠正：`0x5362c218` 实际执行外层准入后跳转解压与 decoded 加和，不等同于完整分区消费/写入验证。下文历史名称“完整解析入口”只能按这个范围理解。CPU 全字段提高的早期内存模型也存在运行 getter 不一致问题；后续以 [保留整个 CPU 的组合包研究](gr3-anniversary-downgrade-followup-2026-11-03.md) 为当前研究方向。

本研究只读取本地官方固件，在进程内存中组成拟第一阶段容器，并分别执行严格主机解码和原厂 ARM 校验代码。没有生成或保存 BIN/ZIP，没有相机、SD 或网络写入。`installation_allowed`、`camera_verified`、`stable`、`bin_emitted` 均为 `false`。这些结果不能称为二阶降级稳定或相机已验证，也不能据此开放网页入口。

`scripts/probe_gr3_anniversary_container.py` 在读取后先固定整包 SHA，再调用已有主机严格导入检查和帧解码，获取精确分区边界。两款拟包只允许下列逻辑改动：

- 外层 `0x38`、`0x50` 两处版本。
- RTOS 内 `0x2038` 版本和 `0x6286cc` 一条指令：`e42103e3 → e6ffffea`，即运行地址 `0x536286cc → 0x5362866c`。
- CPU 内 `0x90` 版本和 `0x7c` 大端加和补数。
- decoded 末尾加和补数；外层 encoded/decoded 长度和末尾加和补数。

探针逐字节比较整个 decoded，拒绝上述固定范围之外的任何变化。14 个逻辑分区中，12 个保持原始完整字节，RTOS/CPU 的非目标字节也保持原样，未改变任何分区头、布局或其余运行指令。复用原压缩帧时同时检查前方 8191 字节字典；改动影响的帧在内存中以 literal 帧替换。重新严格导入并独立解码后，decoded SHA 必须与目标完整一致。此候选的来源属性仍为 `unverified`，不会因结构正确变成官方认证固件。

## 实际执行的原厂 ARM 范围

两款精确新版输入均执行原始 RTOS；只有诊断输出 `0x536b83c4` 返回值被替代，未替代项目号、类型、加和、分区数据或解压结果。

| 入口 | 实际执行内容 | 证据限度 |
| --- | --- | --- |
| `0x5362be30` | 外层项目号、前后项目 magic/marker、类型与全容器加和 | 不解压，不检查压缩帧/分区完整性 |
| `0x5362bf98` | 完整 decoded 流加和 | 不解析每个分区 |
| `0x536291b8` | CPU 项目号、内部双 magic/marker 和 CPU 加和 | 不写 RX Flash，也不执行 RX 固件 |
| `0x5362bd64` | 从严格主机解码所得的完整 decoded 搜寻 CPU，返回精确偏移与131072字节长度 | 不替代原硬件解压或完整分区解析 |
| `0x53628c94` | 类型5和未知类型7的真实返回0路径 | 未运行有效类型的设备派发 |
| `0x5362c218` | 真实完整解析入口先执行外层校验 | 到达 `0x5362c038` 即停止，没有报告完整解析成功 |

每款 15 个 ARM 场景：官方外层、内存拟包外层、4 个外层负例、正确/损坏 decoded 加和、CPU分区精确查找、2个不支持类型拒绝、3 个 CPU 校验场景、1 个完整解析入口边界。主机另外对完整拟包和4个外层负例做严格导入检查。

### 不能省略的负面结果

错误机型和错误类型都先修复外层加和，再交给原 ARM，均被拒绝；不是靠坏校验偶然拒绝。CPU 错误机型也先修复 CPU 加和，原 ARM 仍拒绝。单独损坏外层、decoded 或 CPU 加和均被对应原校验拒绝。

将 payload 整段截掉，只保留 128 字节头和24字节尾，再修复外层加和，原厂**外层校验返回成功**，严格主机解码拒绝。此结果证明外层校验通过不足以证明整包可刷；不能把这个局部返回值包装成原厂完整解析通过。

静态指令还显示原实现存在条件跳过加和的约定：外层 footer 的 `+0x14` 为 `0xffffffff` 时，`0x5362bdb8` 直接成功；CPU `+0x7c` 为 `0xffffffff` 时，`0x53629134` 直接成功。探针未利用这些约定构造拟包；主机严格校验仍要求实际加和为零。这两条为静态来源说明，未计入已执行负例。

## 完整解析为何仍被阻断

真实调用链为：

`0x5362c218 → 0x5362c038 → 0x536b5d4c → 0x537f9438`

`0x5362c038` 从真实 footer 取 encoded/decoded 大小，分配 decoded 缓冲，执行缓存相关操作，再请求解压。后续不是纯 ARM 软件解码循环：

- `0x538580d0` 配置 `0x1b030004`、`0x1b03002c`。
- `0x53858140` 配置 `0x1b030008` 与输入/输出地址 `0x1b030018..0x1b030024`。
- `0x53857fbc` 设置 `0x1b030004` 启动位。
- `0x53857fd8` 调用事件等待，再读取 `0x1b03003c..0x1b03004c` 和 `0x1b030030`。
- `0x538583d0` 读取 `0x1b030038` 状态。

没有该硬件块及完成事件的真实模型，就无法忠实执行原厂解压完成路径。用主机输出填充内存并返回成功会替换关键证据，本探针没有这样做。主机两套严格解码以及最终 decoded 一致，只证明主机算法对内存容器可逆，不证明原硬件解压接受。

## 元数据与 Flash 派发的静态定位

`0x5362a9ac` 在完整解析后取 decoded，`0x5362bd64` 搜寻 flag 低16位为7的 CPU 分区；CPU wrapper 使用 `0x536291b8`。`0x53628c94` 按真实类型跳表设置并派发：类型0/1至 DSP `0x53629a0c / 0x53629a38`，类型2/3/4至组合 `0x5362a994 / 0x5362a9ac`，类型6至 CPU `0x5362911c / 0x53629338`，类型5/default返回0。有效类型的上述派发是固定输入的静态控制流，未运行完整分区解析或写入派发；CPU分区查找及类型5/7拒绝单独执行了原指令。

后续 `0x53628db0` 会进入 CPU `0x5362971c`、组合 `0x5362aa8c / 0x5362aac4` 或 DSP `0x5362a5b0` 的更新流程，涉及驱动、设备和持久化状态。没有把这些入口替换成恒成功，也没有执行 Flash 操作。
