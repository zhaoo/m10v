## Current serialized state, not historical104-byte state

`native/gr3/m10v_library.h::m10v_library_state` is184 bytes with ten8-byte slots and ten8-byte effect records. `m10v_library_init()` and `m10v_library_valid()` in `m10v_library.c` use magic0x5630314d, schema version5, size184. Fields: slots12..91, watermark92..95, effects96..175, global reserved176..179, CRC180..183. CRC covers the first180 bytes.

Current journal names are `M10V6A.bin`/`M10V6B.bin` in `m10v_library_camera.c`. They are schema5 despite the filename6. `store()` chooses sequence parity, writes with stock FS wrapping, rereads, validates and compares all bytes before publishing preview cache. `commit()` in the pure library updates sequence/CRC and copies into caller state only after store succeeds. Preserve this failure atomicity.

Global reserved bit0 is film-name watermark. Bits1..4 and5..8 encode paired old/new slot indices for pending legacy-selection reconciliation. Validator permits only mask511 and requires either both migration fields zero or both nonzero, old<=5,new<=10. Preview publishing/reading, producer and render reject `reserved & 510`, intentionally suppressing states with pending remaps. Per-slot `effects.reserved[0]` is custom-record bank and `[1]` is Charmera/anime mode; neither is free.

### Chosen implementation: independent journal and cache

The coordinator chose a separate border journal rather than extending film state. The analysis above records why no existing reserved bytes can be reused without additional migration work; **no library schema, film-state bits, SD record or existing journal was modified**.

`native/gr3/m10v_border_camera.c/.h` now defines border enum0/1/2 and a24-byte A/B record: magic0x31524442, version1, sequence, style, reserved0, CRC32 over first20 bytes. Filenames `BORDERA.BIN`/`BORDERB.BIN`; sequence parity chooses target. Only a valid CRC/schema/enum record participates in latest selection; corrupt latest falls back to the other page. Missing valid records defaults off. Save verifies exact readback before publishing; sequence overflow and invalid enum reject. Existing FS service wrapping matches the independently tested HDF journal contract.

The Effects page contains a16-byte `m10v_border_cache` at page+0x194; the expanded controller is0x1a8, still under0x1c0. Its fields are magic, publication version, style and journal sequence. `m10v_border_camera_refresh(owner)` and `save(owner,style)` are UI/filesystem-safe APIs. `cached()` performs only original TopMenu singleton lookup and bounded stable publication read, with no FS/allocator/wait. Build must supply `M10V_BORDER_CACHE_OWNER_OFFSET = actual Effects owner offset + 0x194` to **both** backend and menu. The current default combined snapshot build uses0x23d0 =0x223c+0x194. Static assertions enforce the shared layout.

`m10v_border_camera_snapshot(uint32_t *outstyle)` returns1 only for stable valid cache (including genuine off), and0 for missing/busy/invalid cache without touching output. Capture must use this status API. The convenience `cached()` returns off on unavailable state and is not proof of selection. The cache is loaded by Effects ready; startup integration should refresh it from `native/gr3/m10v_ab_camera.inc::m10v_settings_controller_ab_live_enter()`, route0x08000000, after its existing retained-TopMenu factory call. This hook already performs legacy reconciliation and film cache load on the UI lifecycle. Refresh only when the border status is unavailable. Constructors remain allocation-only to avoid known factory reentry. There is no `m10v_sd_camera_ready()` in the inspected tree; SD camera line168 is film installation and does not run on boot.

The grouped Effects menu now has HDF/border root focus and a border child with three draft choices. It reuses existing widgets, route, owner capacity and original HDF behavior. Cancel does not write, confirm stores/readbacks, failure stays open with error and reconciles actual journal value. `M10V_BORDER_ENABLED` defaults0 and hides all border behavior; `M10V_HDF_ENABLED` defaults1 and can be0 for a border-only menu without references to HDF load/save. The main build now accepts `border_enabled=False` (CLI `--border-enabled` is explicit opt-in), links backend and menu only when enabled, and keeps normal callers at false. It rejects non-owned film/SD lifecycle configurations. Manifest marks hardware_ready=false and pixel_pipeline_enabled=false; Node firmware export rejects an enabled border menu/cache runtime until a hardware compositor is installed. New captions1150=边框,1151=拍立得,1152=胶卷; off reuses972. Existing resource numbers remain fixed.

## True per-shot freeze and strict memory limits

`m10v_isp_recipe_color.c::m10v_isp_frame_recipe_producer()` is hooked by `scripts/build_gr3_isp_recipe_color.py` at GR III processing-task producer0x5351ea9c, before its first queue message. It reads only the already-published owner cache, verifies no mutation, confirms cache sequence and ShootingInfo identity/tone, then calls `m10v_isp_frame_recipe_snapshot()` once. The snapshot copies the **entire film state**. The independent border enum still requires a separate per-shot freeze; no border field was added to this film snapshot. Do not reread border from FS or current UI at Still Make/encoding time. `0x5351ae2c` is retirement, not the capture producer.

Owner preview cache is at TopMenu+0x213c,256 bytes; header8 plus current state184 is192 bytes. `owner_cache = live_color || (recipe_snapshot && sd_library)` in build script deliberately supports still freeze even with live preview off. Preserve that distinction. Existing film publication remains unchanged; border has a separate owner cache.

Recipe color is1796 bytes at recipe+0x4a08, compile-time asserted in `m10v_isp_recipe_color.c`; it ends at0x510c. RAW token begins0x5110 and is48 bytes, extended allocation ends0x5140. Only4 bytes separate color extent and RAW token. Growing the state would require coordinated owner allocation, offsets, clearing/copying, static assertions, independent JS/Python readback contracts and RAW lifetime tests. The coordinator is separately auditing the four-byte gap at color+0x704 as potential scalar border freeze storage; this subtask does not implement that write.

Do not borrow token reserved words: current shared HDF uses `m10v_capture_raw_lifetime.reserved[3]`, physically at0x5134..0x513f. `scripts/build_gr3_digital_hdf.py` and its JS checker still report shared_offset0x50e4; that is stale metadata relative to current C, not evidence of free memory. This unrelated mismatch should not be used to place border metadata.

`m10v_isp_frame_recipe_state()` retrieves the shot copy and `completed()` compares full bytes, sequence, recipe and ShootingInfo. Border execution needs a separate completion contract bound to recipe, frozen enum and geometry. `M10V_NATIVE_COLOR` does not authenticate borders. A scalar enum can fit existing state; output buffer ownership/completion/geometry need a separately audited extension rather than pretending unused color mask bits are sufficient.

### Global does not currently mean all tone paths execute capture bridge

Producer accepts stock tones11..22 and appended25..34, so it can freeze global state even for stock controls. However `m10v_library_capture.c` maps SI/snapshot tone into a film slot and rejects `slot==M10V_SLOT_COUNT` at its line264, before image processing. `m10v_library_cpu_stages()` also requires a valid nonempty film slot. Therefore a global border cannot merely be tacked onto the film residual renderer; it needs its own stock-safe hardware stage reachable independently of film slot, with default-off yielding zero work. Never fabricate slot0/color completion for stock controls to bypass this gate.
