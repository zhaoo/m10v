# 从历史二阶包继续研究周年固件降级

> 后续复核纠正：下述最早“CPU 第三段提高为21”的内存模型只验证过替代 getter 下的局部门禁。真实 RX getter 的第三段来自指令常量20，修改 CPU 头并不会同步改变运行报号。因此它不能直接用作硬件候选。后续研究改为完整保留官方 CPU、保留组合 kind2，见 [后续报告](gr3-anniversary-downgrade-followup-2026-11-03.md) 与 [CPU 指令证据](gr3-cpu-anniversary-delta-2026-11-03.md)。没有放宽网页导入或安装门禁。

## 用户补充与历史包身份

2026-11-03 用户补充：此前二阶包曾成功，机身为店内刷入、官网未公开的 30 周年特殊服务版本，记忆中介于 2.10 与 2.20 之间。未取得该次机身完整 DSP/CPU 版本或新的实测记录；不把“介于两个版本”当作确切内部数值。

只读核对本地历史 ZIP `M10V-GRIII-bridge-2.10.22.27.zip`：归档 SHA-256 `17ebc9d716485ac6715c02cdab935761e296c0af6e4b2392fd03d946e9e0b9b4`，第一阶段 BIN 为 `e49cce2858e52b200b9d451100d13f3ff7ea51f30b66503cb26d503851431955`、版本 2.10.22.27；第二阶段是精确官方 2.10 `d6a3c9c288d784080e7b283222ecdd8752adfeed6faa36dab44f73115354bfd4`。未复制或重新交付旧 BIN。

历史成功可以启发桥接结构，不足以证明官网 2.20、其他服务组件或黑屏故障机可用。仓库既有记录另有一阶失败反馈与 DSP 2.10.32.27 的照片证据，它们不应覆盖用户刚补充的某次成功，也不能混为同一台/同一版本的验收。

## 新方案与历史路线的差异

既有二阶结构分两步解决问题：第一包先被正在运行的更新器接受；第一包安装后的更新器再允许恢复较低版本。仅修改待刷包里的比较指令不能影响安装前机身现存更新器。

对公开 2.20 的研究方向调整为：

1. 第一阶段保留精确官方 2.20 的全部运行代码与分区布局，只拟提升四处包版本、修复相应校验并修改该版原厂更新器的一条拒绝分支；不放入 M10V 胶卷/菜单运行体、不使用 2.10 替代第一阶段运行体、不做原生地址重定位。
2. 第一阶段完整安装并正常启动后，才研究由其更新器恢复精确官方 2.10。第二阶段还会将桥接更新器覆盖回官方实现。

局部试验的第一阶段拟定组件包号为 GR III `2.20.21.28`；IIIx 对照为 `1.70.21.18`。它们是合成研究值，不是官方发布版本、实际机身版本、已构建候选或已验证安装包。高于它们的未知服务组件继续被原比较拒绝，不寻找任意超大版本值绕过。

这一路线减少了第一阶段对原厂运行体的改动，但不构成风险已量化或一定安全的结论。尤其第二阶段会切回旧版运行代码，NVRAM/原厂设置格式、升级持久化副作用和完整启动仍未知。

## 新版地址的独立核对

在本次两份精确官方周年原包上读取代码后，确认拒绝入口为 `0x536286cc`，原字节 `e42103e3`；内存探针改为 `e6ffffea`，经 Capstone 确认无条件分支至原成功返回 `0x5362866c`。旧 2.10 二阶包的地址是 `0x536285dc→0x5362857c`，原字节不同，不能照搬补丁地址。

探针逐字节确认原 RTOS 除这条内存补丁外均保持原样。组件候选字段及 CPU 补数只在内存中构造，没有把它们封装成最终更新容器；不能报告为最终 BIN 校验通过。

## 实际执行的离线研究

`scripts/probe_gr3_anniversary_downgrade.py` 对来源完整 SHA、严格解码、具体机型项目号固定身份，随后用 Unicorn 执行真实周年更新器。只有当前 DSP/CPU getter 和诊断输出由测试替身提供，不执行 Flash IO。

| 场景 | GR III 2.20 | IIIx 1.70 |
| --- | ---: | ---: |
| 原厂更新器对拟第一包：6 类型 × 5 组独立 DSP/CPU 值 | 30 | 30 |
| 原厂更新器对旧 GR III 2.10.22.27 桥接字段 | 6 | 不适用 |
| 第二阶段精确旧官方包：原厂拒绝与内存补丁准入对照 | 12 | 12 |
| 两种更新器的原新/旧官方 CPU、拟 CPU、坏加和、错误机型 | 10 | 10 |
| 空候选拒绝 | 2 | 2 |
| 合计 | **60** | **54** |

全部场景的预期得到验证。旧 GR III 2.10.22.27 字段被实际官方 2.20 更新器拒绝；新版保留运行体的桥接思路能通过所测局部版本门禁，并且 CPU 坏加和/错误型号仍被拒绝。

3 个 Python 行为回归通过，覆盖未知型号在读取文件前拒绝、GR III 旧桥接拒绝/新桥接局部准入、IIIx 正确来源及硬件门禁保持关闭。JSON 结果位于本地忽略目录 `builds/firmware-safety-audit-20261103/gr3-220-minimal-bridge-probe.json` 与 `gr3x-170-minimal-bridge-probe.json`。探针和 CLI 均 `installation_allowed=false`、`bin_emitted=false`，研究通过退出码 2。

## 当前不能推导的结论

- 没有完整第一阶段 BIN，也没有执行真实整包解析、解压、Flash 擦写、校验和状态机；不能称为降级包已做完。
- 没有第一阶段安装/冷启动、菜单、拍摄/回放验证；局部成功返回不等于相机能启动。
- 没有证明第二阶段的旧官方运行体能安全解释已被新固件写入的持久化状态，不能靠重置设置或删除用户文件猜测解决。
- 未知店内服务版缺少完整组件号及更新器字节，公开固件的测试不能代替其验收。
- 黑屏且 MENU/回放启动均不可用的事故机没有可用的本方案入口；本研究不是 SD 救砖。
- 未读写用户相机/SD；现有 2.10 / 1.60 生成器、原生代码、来源门禁保持不变。

下一阶段应先具备可硬件恢复的专用测试条件，再决定是否封装最小第一阶段候选并开展分阶段设备验收。不能使用用户当前正常的 2.10 相机承担这项研究，也不能把历史某次二阶成功当作公开 2.20 跨版本恢复的保证。
